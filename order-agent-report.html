Order Inquiry Agent — Implementation Report

Second agent application (30%) · EZStore quotation & order system

Scope: agent/order_agent/, mcp_server/server.py Model: gemini-3.1-flash-lite Date: 2026-10-28

Architecture

A second ADK app in the existing agent container and port 8080 (/apps/order_agent). It has no write path, adds no service and changes no backend. The graph has exactly one LLM node, classify_intent; guards, routing, arguments, clarification, refusal and error handling are deterministic Python. The tools are read-only: get_order, list_orders, order_summary. Status accepts only pending / confirmed / completed / cancelled; anything else is explained and clarified rather than silently returning every order. Off-topic requests, quotation operations, write requests and the “bare order number after a clarification” turn are designed not to reach the model; in one automated pass, the 8-turn acceptance set used 4 calls.

Same page, different app. Both agents use the same Chat UI component; the only difference is the ?app= query. /agent → quotation_agent; /agent?app=order_agent → order_agent. The value is sent as the app name in /apps/{app}/users/.../sessions and /run_sse.

Use cases

Handoff from the quotation agent

The quotation agent's guard detects the order domain before calling its classifier, so the handoff costs one order-agent classifier call and no quotation-agent call. The reverse still holds: the order agent refuses quotation operations and any order write (for example, changing the status to “已出貨”) and points the user to the quotation agent or to manual processing in the UI.

Two findings worth recording

  1. The eval initially graded the wrong agent. agents-cli reads agents-cli-manifest.yaml (agent_directory: quotation_agent), so in-process inference ignored --app-name. The first run produced quality 5.0 but refusal 0.0; reading the per-case reasons showed the replies were quotation-agent refusals. Switched to a local server plus --url and --app-name order_agent, and documented the commands in agent/README.md. A plausible average does not prove the right thing was graded.
  2. Retries and budget. At most 3 attempts per model call, then a fixed manual-intervention reply; auth/MCP/seed failures are never retried. Our call log recorded 34 of 50 calls, including one failure (an 8 s timeout rejected by the API; raised to 10 s) and 9 calls spent grading the wrong agent.
Read-only by design: the agent is given no MCP tool that mutates data, and the refusal and clarification paths are written to call no tools at all. A spot check after one run matched the seed data; this was not an exhaustive audit.
